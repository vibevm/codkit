# Тип проекта

Тип проекта — знание Codkit об одном семействе апстримов: где лежит собственный
код, какой файл является манифестом продукта, чем подменяется сервис, как дерево
собирается и тестируется, какие изображения несёт дистрибутив. Движок
универсален и спрашивает тип; сам он фактов типа не называет
([PROP-016](../../../../vibevm/vibespecs/modules/codkit/PROP-016-project-types.xml)).

Один patch set объявляет ровно один тип. Тип поставляется отдельным npm-пакетом
и входит в комплект поставки ([08](08-release-ci.md#поставочный-комплект-air-gapped)).

## Что несёт установка

1. `codkit types` → строка на каждый зарегистрированный тип: идентификатор,
   пакет, версия и список возможностей, затем перечень имён возможностей
   контракта; exit `0`. Patch set не нужен.
2. `codkit --json types` → `data.types[]` с полями `id`, `package`, `version`,
   `installed`, `capabilities` и `configurableCapabilities`. `installed: false`
   означает, что реестр знает идентификатор, а пакет в этой установке не лежит:
   доставь его комплектом
   ([08](08-release-ci.md#поставочный-комплект-air-gapped)), а не из сети.
   `configurableCapabilities` (в человеческом выводе — строка
   `from typeConfig:`) — возможности, которые тип объявляет только для patch set,
   попросившего о них секцией `typeConfig`.
3. `codkit where` печатает строку `project type: <id>`; `codkit --json where`
   несёт тот же идентификатор в `codkit.type` (значение `null` — конфигурация не
   прочитана либо patch set не выбран).

Набор типов фиксирован релизом инструмента: реестр — таблица имён пакетов внутри
CLI-пакета, и ни один модуль не грузится из patch set или из произвольного пути.
Появление нового типа — новая версия Codkit, а не правка конфигурации.

## Два поля конфигурации

`codkit.json` схемы 2 объявляет тип двумя полями:

```json
{
	"codkitConfig": 2,
	"type": "vscode",
	"typeConfig": { "ownRoot": "src/vs/patchset" }
}
```

- `type` — идентификатор из `codkit types`;
- `typeConfig` — секция, которую валидирует сам тип. Первое поле секции,
  `ownRoot`, — полный путь собственного кода от корня дерева; остальные поля
  секции движок не читает.

Схемы 1 больше нет: слоя совместимости не существует, и ни один путь кода не
выводит тип по догадке.

## Тип `generic`

`generic` — простой git-апстрим без модели продукта: ни расширений, ни подмены
сервисов, ни входного модуля, ни dev-канала, ни изображений дистрибутива, ни
рантайм-библиотеки. Он существует, чтобы `load|save|verify|cycle|publish|ci`
работали над любым апстримом до того, как у этого семейства появится
собственный тип.

Всё, что он отвечает, объявляет сам patch set — поэтому у него в `codkit types`
пусто в `capabilities` и две возможности в `from typeConfig`:

| Поле `typeConfig` | Что задаёт |
| --- | --- |
| `ownRoot` | собственный корень: любой каталог дерева |
| `commands.install` | чем ставятся зависимости дерева |
| `commands.lint` | гейты гигиены и линта, по порядку |
| `commands.compile` | каналы компиляции: скрипт и границы прохода; объявлен хотя бы один — есть возможность `build-channels` |
| `commands.test` | `{command, ownGlobArg?}`; глоб — `<ownRoot>/**/*.test.*` |
| `overlayTargets` | JSON-цели слоя `config-overlay` (без dev-канала); объявлена хотя бы одна — есть возможность `config-overlay` |
| `cleanupWhitelist` | что свежий проход вправе удалить |
| `identity.manifest` | `{path, nameField?}` — файл, который patch set называет доказательством своего апстрима (объявление; `check-tree` пока проверяет только git-условия) |

Практические следствия: `imageset *`, `gen brand`, `runtime load|check` над
таким patch set всегда отказывают `CK-E-TYPE-CAPABILITY`; `build *` отказывает,
пока не объявлены `commands.compile`; overlay материализуется только
`codkit overlay apply <файл>`, потому что dev-канала нет. Заведение такого
patch set по шагам — [02](02-daily.md#патч-сет-над-апстримом-без-модели-продукта).

## Отказы и что по ним делать

| Наблюдаемый отказ | Что означает | Шаг |
| --- | --- | --- |
| `CK-E-CONFIG: is schema 1: schema 2 adds type, typeConfig.ownRoot ...`, exit `2` | patch set остался на схеме 1 | выполни подсказку отказа: `codkitConfig: 2`, добавь `type` и `typeConfig.ownRoot`, удали `ownDirName` |
| `CK-E-TYPE-UNKNOWN: the project type "<id>" is not in the registry of this codkit`, exit `2` | идентификатора нет в реестре этой установки | `codkit types`; либо исправь `type`, либо поставь установку, где этот тип есть |
| `CK-E-TYPE-UNKNOWN: ... is installed but does not answer its own contract`, exit `2` | версия пакета типа не соответствует контракту этого Codkit | поставь комплект целиком: CLI и пакеты типов одной версии |
| `CK-E-CONFIG: typeConfig.<поле>: ...`, exit `2` | секцию отверг сам тип | исправь поле по тексту отказа; границы секции задаёт тип, а не движок |
| `CK-E-TYPE-CAPABILITY: <что> needs the capability <имя>, and the project type <id> does not declare it`, exit `2` | глагол требует возможности, которой у типа нет; ничего не записано | `codkit types` покажет, что тип отвечает; выбери слой/глагол из отвеченных |

## Возможности типа

Возможность — именованная необязательная способность, которую тип объявляет.
Матрицу печатает `codkit types`; глагол, которому нужна отсутствующая
возможность, отказывает `CK-E-TYPE-CAPABILITY` до первой записи.

| Возможность | Что она открывает | Кто отказывает без неё |
| --- | --- | --- |
| `brand-images` | набор изображений дистрибутива | `imageset gen/index/verify` |
| `gen-brand` | таблица бренда и прививка строкового шва | `gen brand` |
| `build-channels` | каналы компиляции за обёрткой | `build up/down/status/errors` |
| `runtime-library` | поставляемый рантайм ([14](14-runtime.md)) | `runtime load/check` |
| `config-overlay` | лист `config-overlay` дерева решений [03](03-interventions.md) | `verify` над артефактом overlay |
| `own-extensions` | лист `own-extension` | `verify` над записью расширения |
| `service-override` | лист `service-override` | `verify` над записью подмены |
| `entry-module` | лист `entry-module` | `verify` над прививкой входного модуля |
| `dev-channel` | dev-канал рядом с целью overlay | отдельного отказа нет: без канала его просто не существует |
| `upgrade-advisory` | семантические читатели советника в `codkit cycle` | отдельного отказа нет: без читателей советнику нечего сообщить |

Слои `own`, `patch`, `resource-file` и `rewrite-rule` есть у любого типа.
Остальные листы лестницы существуют ровно тогда, когда возможность объявлена:
`verify` над артефактом слоя, которого у типа нет, — тот же
`CK-E-TYPE-CAPABILITY`.

## Завести patch set нужного типа

1. `codkit types` → выбери идентификатор; exit `0`. Идентификатора нет —
   останов: нужный тип в этой установке не поставлен, и конфигурацией это не
   лечится.
2. Запиши в `codkit.json` поля `type` и `typeConfig.ownRoot` (пример выше).
   `ownRoot` — путь от корня дерева; тип отвергает путь вне своих границ
   отказом `CK-E-CONFIG` с текстом, объясняющим границу.
3. `codkit where` → строка `project type: <id>` и exit `0`. Exit `2` —
   исправляй ровно названное поле и повторяй шаг 3.
4. `codkit check-tree --require-clean` → exit `0`: отпечатки дерева спрашивает
   тот же тип. Exit `1`/`2` — действуй по [02](02-daily.md#получить-дерево).
5. `codkit verify` → exit `0`. Красный `CK-E-TYPE-CAPABILITY` означает, что в
   дельте лежит артефакт слоя, которого у этого типа нет: перенеси изменение в
   слой из таблицы возможностей ([03](03-interventions.md)).
6. Дальше — обычный день [02](02-daily.md#цикл-дня); ни одна команда не просит
   называть тип повторно.

Смена типа готового patch set — не операция Codkit: дельта, инвентарь и
доказательства написаны против одного семейства апстримов. Другой тип — другой
patch set.

## Что делает тип, а что движок

| Спрашивает движок | Отвечает тип |
| --- | --- |
| Собственный корень, каталог расширений, whitelist очистки | путь и списки семейства |
| Какие слои существуют | набор возможностей |
| Чем собирать и тестировать | шаги сборки, каналы компиляции, глоб тестов |
| Что изменилось между пинами | семантические читатели советника |
| Какие изображения несёт дистрибутив | таблица целей и кодеки контейнеров |
| Скелет фичи и прививка бренда | шаблоны генератора |

Движку принадлежат грамматика маркеров, бюджет прививки, страж дрейфа,
генерируемая ветка, транзакции цикла, лицензирование и протокол стандартов.
Ни один из этих механизмов у типа ничего не спрашивает.

## Норма → механизм

| Норма | Механизм | Наблюдаемый отказ |
| --- | --- | --- |
| Patch set объявляет тип явно | схема 2 требует `type` и `typeConfig.ownRoot` | `CK-E-CONFIG`, exit `2` |
| Загружается только код релиза инструмента | реестр имён пакетов внутри CLI-пакета | `CK-E-TYPE-UNKNOWN`, exit `2` |
| Глагол вне способностей типа не делает вид, что сработал | проверка возможности до первой записи | `CK-E-TYPE-CAPABILITY`, exit `2` |
| Версии CLI и пакетов типов совпадают | комплект поставки ставится одной командой | `CK-E-TYPE-UNKNOWN` о контракте, exit `2` |
