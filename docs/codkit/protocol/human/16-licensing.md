# Лицензия продукта: один источник, все поверхности

Лицензионная поза продукта — решение правообладателя, и у неё одно место хранения: профиль
организации в доверенном хранилище машины `~/.codkit/organization-policies.json`
([PROP-019](../../../../vibevm/vibespecs/modules/codkit/PROP-019-organization-licensing.xml)).
Patch set только **выбирает** профиль файлом `codkit.licensing.json` и добавляет в нём блок
`product` с тем, что относится к показу, а не к праву: имя файла лицензии, человеческое название
лицензии для заголовков, какого из держателей профиля называют уведомления, год, адрес, и
«отставленные уведомления» — фразы прежней позы, которые не должны пережить переход.
Ничто в patch set не может расширить право: держатель вне профиля, свой текст, своё разрешение —
`CK-E-CONFIG`.

Что из этого делает инструмент, а что — семья апстрима, разделено контрактом типа: область
`licensing` ([PROP-016](../../../../vibevm/vibespecs/modules/codkit/PROP-016-project-types.xml),
`TYPE-AREA-LICENSING`) отвечает, в какой форме own-файлы несут заголовок, где лежит файл лицензии
продукта, какие поля манифестов называют лицензию, какие файлы апстрима несут его собственные
условия, что читает инсталлятор вместо текста, где собираются лицензии компонентов и где живёт
сторожевой тест. Движок читает профиль, раскладывает заголовки, пишет артефакты, сканирует и
отказывает; тип ничего не пишет. Тип `vscode` область отвечает
([vscode PROP-010](../../../../vibevm/vibespecs/modules/vscode/PROP-010-licensing.xml)); тип без
области всё равно получает заголовок из профиля и проверку носителей в `verify`, а `gen licensing`
над ним отказывает `CK-E-TYPE-CAPABILITY`.

## Четыре шага

1. **Профиль на машине.** Администратор или владелец кладёт профиль в хранилище: держатели,
   собственное лицензионное выражение (при необходимости по областям путей), одобренные и
   запрещённые выражения третьих сторон, канонический текст каждой `LicenseRef-`-лицензии с его
   SHA-256, требования к уведомлениям поставки. Patch set пишет `codkit.licensing.json` версии 2:
   `profile`, `componentId`, `created`, `sourceDirectory` и блок `product`. Машина, которая запускает
   `verify` — машина CI включительно — обязана нести профиль: иначе один finding
   `CK-E-LICENSE-PROFILE`, и никакой запасной копии внутри patch set не читается.
2. **`codkit gen licensing --owner <владелец>`** — пишет поверхности из профиля и ответа типа
   (`GEN-LICENSING`): overlay-операции полей манифестов (слиянием в существующий overlay цели,
   `expectUpstream` — значение на пине), add-file патч файла лицензии с каноническим текстом,
   лицензии компонентов под каталогом компонентов (условия апстрима с пина байт в байт; текст
   самого Codkit, когда в own-слой доставлена его библиотека рантайма), рендеры для инсталлятора
   (RTF из того же текста) и сторожевой тест. Нужны оба корня: байты пина берутся из дерева.
   Патчи поверхностей не несут маркерных блоков: это документы, которые продукт поставляет
   дословно, и `verify`/`save` относят их к артефакту по пути (PROP-006 `LICENCE-DOCUMENT-EXEMPTION`).
   Повторный запуск без `--update` — `CK-E-GEN-EXISTS`, ничего не записано; `--update` переписывает
   ровно артефакты этой команды — так приезжает новая редакция текста; `--dry-run` печатает план.
   В конце — напоминания: объявить unit для guard в `delta/own/patchset.delta.json`, запустить
   `license annotate --own`, запустить `verify`.
3. **`codkit license annotate --own [--replace-retired] [--dry-run] [<пути…>]`** — даёт own-файлам
   носители из профиля (`ANNOTATE-OWN`): обходит `delta/own/**`, `delta/own-roots/**` и own-расширения
   (пути сужают обход; путь, под которым нет own-файлов, отклоняется — опечатка не должна выглядеть
   как сделанная работа), пропуская доставленное инструментом (`delta/own/codkit/**`) и own-манифест;
   файл с синтаксисом комментария
   получает заголовок семьи (у `vscode` — линованный блок апстрима для `.ts`, `.js`, `.css`,
   комментарий расширения для остальных), файл без него — sidecar `<имя>.license` в две строки.
   Файл, уже несущий носитель с держателем профиля и собственным выражением, — `unchanged`;
   носитель, не соответствующий профилю, — `foreign-holder`, и файл не трогается. Флаг
   `--replace-retired` заменяет **только** ведущий блок комментария файла (или sidecar целиком), в
   котором есть строка copyright и фраза из `retiredNotices`: чужое уведомление без такой фразы —
   уведомление третьей стороны, и переписывать его нельзя; носитель глубже ведущего блока тоже не
   трогается. `--year`, если дан, должен совпадать с годом профиля; флаги пакетной формы (`--dir`,
   `--third-party`, `--holder`, `--license`, `--source`) с `--own` не сочетаются. Все решения
   принимаются до первой записи: отказ (нечитаемый реестр, файл с CR) оставляет патчсет как был.
   Аннотации `REUSE.toml` уважаются как в проверке: каталог файлов данных покрывается одной
   собственной аннотацией вместо sidecar на каждый файл, производный от третьей стороны каталог
   объявляется аннотацией `third-party; <происхождение>` и остаётся нетронутым. Ресурсы
   (`delta/resources/**`) не обходятся: ресурс, заменяющий файл апстрима, — производная работа,
   пока человек не сказал иного; его аннотируют по пути осознанно.
4. **`codkit verify`** — при наличии декларации добавляет три проверки (`VERIFY-LICENSING`):
   профиль (`CK-E-LICENSE-PROFILE`), носители own-слоёв (`CK-E-LICENSE-HEADER` на файл) и
   поверхности типа — каждое поле выставлено overlay'ем в ожидаемое значение, add-file патч файла
   лицензии несёт канонический текст, лицензии компонентов и рендеры объявлены, guard записан
   (`CK-E-LICENSE-SURFACE`). Без декларации `verify` работает как прежде.

## Сторожевой тест

`gen licensing` пишет guard по пути типа (у `vscode` — `delta/own/test/node/licence.leftovers.test.ts`,
слова раннера `suite`/`test`) с id сюиты `licence-leftovers`; поверхности называют его в
`contract-tests`, а `verify` находит его как любой guard. Он работает в дереве форка под собственным
прогоном тестов продукта и без инструмента: у каждого файла own-корня и own-расширений
(каталог Codkit исключён) есть носитель — заголовок, sidecar или аннотация `REUSE.toml`; ни одна
отставленная фраза не встречается ни в own-файлах, ни в файле лицензии, рендерах и лицензиях
компонентов; файл лицензии побайтно равен каноническому тексту (SHA-256 зашит); поля манифестов
читают ожидаемое; лицензии компонентов существуют.

## Переход с неверной позы

Если продукт уже несёт неверные заголовки или поставляет лицензию апстрима как свою, порядок
такой: профиль в хранилище и декларация с `retiredNotices` (прежние фразы и прежний держатель);
`gen licensing` (с `--update`, если поверхности уже были); `license annotate --own
--replace-retired`; затем **собственные доказательства продукта**, которые защищали прежнюю позу —
решение в спецификации, статический тест, правило линтера в патче, тест на имя файла лицензии —
переворачиваются на новую; `verify` до нуля; `codkit load --fresh`; сборка и поиск отставленных
фраз по дереву и по собранному артефакту. Файл лицензии самого репозитория patch set инструмент
никогда не трогает ([13](13-standards.md), `STD-LICENCE-SCOPES`): его владелец пишет сам, тем же
текстом.

## Чего инструмент не делает

Не выдаёт юридических заключений: отчёт говорит «доказательства полны» или «неполны». Не берёт
права из patch set. Не редактирует файлы лицензии апстрима и его уведомления о третьих сторонах:
условия апстрима уезжают в поставку лицензией компонента, а не исчезают. Не ставит второй баннер в
изменённые файлы апстрима: их происхождение — маркеры и инвентарь. Отказ `package`/`publish` при
неполных доказательствах и раздел NOTICE со списком изменённых файлов апстрима — следующая
кампания (`ORGANIZATION-DISTRIBUTION-EVIDENCE`).
