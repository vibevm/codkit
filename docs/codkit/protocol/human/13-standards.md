# Стандарты Codkit в репозитории продукта

Codkit поставляет **набор** vibe-пакетов вида `flow` и доставляет его одним прогоном. Универсальная
половина набора приезжает в любой patch set, чем бы он ни форкал:
`org.vibevm.codkit/standards` — нормы для patch set (издание 1.0.0: минимальное вмешательство в
форк) — и `org.vibevm.codkit/agent-skills` — навыки агентов (`ck-orient`, `ck-intervene`,
`ck-review-intervention`, `ck-resolve`), которые менеджер пакетов проецирует в каталоги навыков
харнессов. Разведены намеренно: версия нормы не должна меняться от правки агентской процедуры.
Контракт —
[PROP-014](../../../../vibevm/vibespecs/modules/codkit/PROP-014-standards-and-licensing.xml),
команды — [PROP-007 §23–24](../../../../vibevm/vibespecs/modules/codkit/PROP-007-cli.xml), установка
агентского профиля — [протокол агента](../agent/00-index.md). Все команды ниже — команды человека
или оркестратора: агентская сессия над продуктом их не запускает (они вне read-only allowlist хука).

Вторая половина набора принадлежит **типу проекта** ([15](15-project-types.md)): норма универсальна,
шов — нет. Каталог швов уехал из пакета `standards` в пакет типа: `org.vibevm.codkit/seams-vscode`
у типа `vscode` и `org.vibevm.codkit/seams-theia` у типа `theia` (у каждого свой `vibe.toml`, README,
лицензионные носители и загрузочный сниппет), и каждый доставляется только patch set'у своего типа;
тип `generic` своих пакетов не называет и получает универсальные два. Отсюда
единственное новое требование: `standards load` и `standards check` читают `codkit.json`, чтобы
узнать тип. Дерево форка им по-прежнему не нужно и блокировка не берётся, но patch set без
конфигурации получает `CK-E-CONFIG` («нет типа проекта, который можно спросить»), exit `2` и ни
одного записанного байта; `standards license` корней не требует вовсе.

## Четыре команды

1. `codkit standards load` — кладёт побайтовую копию **каждого** поставляемого пакета в
   `vibevm/vibepacks/org.vibevm.codkit/<имя>/v<версия>/` (сначала `standards`, дальше по алфавиту) и
   ведёт в `vibe.toml` продукта один блок между `# codkit:begin standards` и
   `# codkit:end standards` — по таблице `[requires.packages]` на пакет, каждая с точной версией и
   `link = "static"`. Ожидается exit `0`, строки `next: vibe install --offline` и — раз доставлен
   пакет с навыками — `next: vibe skill install`; повтор — `up to date`, exit `0`, ни одного
   изменённого байта. `--dry-run` печатает план. Дерево форка команде не нужно; `codkit.json` нужен —
   из него берётся тип проекта, а с ним и список пакетов типа.
2. `vibe install --offline`, затем `vibe skill install` в репозитории продукта — материализуют
   пакеты в `vibevm/vibedeps/org.vibevm.codkit.<имя>/<версия>/`, обновляют `vibe.lock`
   (`source_kind = "local"`) и загрузочную полосу и проецируют навыки в `.claude/skills/`,
   `.opencode/skills/`, `.agents/skills/`. Codkit `vibe` не вызывает: это команды подряд, и всё
   коммитится вместе.
3. `codkit standards check` — только чтение, по каждому пакету: копия `identical`, лицензионная
   проверка копии чиста, обе копии `LICENSE-CODKIT.md` на месте и не правлены, блок `current`. Любая
   находка — exit `1` со своей строкой (с именем пакета) и hint.
4. `codkit standards license` — печатает текст файла `LICENSE-CODKIT.md`, рекомендации, строки
   контракта `vibe scrape` (те, что `load` ведёт в контракте сам; см. ниже) и запись
   `[[annotations]]` для собственного `REUSE.toml` продукта. Корни не нужны.

Коммит в продукте после шагов 1–2: каталоги копий, `LICENSE-CODKIT.md` в корне и в
`delta/own/codkit/`, `vibe.toml`, `vibevm/scrape/contract.toml` (если есть), `vibe.lock`,
`vibevm/vibedeps/org.vibevm.codkit.*/**`, спроецированные каталоги навыков, сгенерированные
`vibevm/vibespecs/boot/STATIC.*` и `INDEX.md`.

## Файл LICENSE-CODKIT.md

`load` кладёт уведомление о лицензии Codkit в два места: корень репозитория и `delta/own/codkit/`
(копию издания 2 из `delta/own/` он переносит сам и печатает `moved`). Вторая копия — доставленный
Codkit файл: следующий `codkit load` доносит её в `<ownRoot>/codkit/` дерева, `ci`
коммитит её в свою сгенерированную ветку; юнита в манифесте own она не требует. Уведомление задаёт
область действия путями — всё под `vibevm/vibepacks/org.vibevm.codkit/**` (и проекцией
`vibevm/vibedeps/org.vibevm.codkit.*/**`), под `delta/own/codkit/**` и сам файл принадлежат Codkit и
лицензированы UPL-1.0, вне этих путей оно ничего не лицензирует — и несёт блок компонентов
(`codkit:begin components`), который каждая доставляющая команда (`standards load`, `runtime load`)
переписывает по факту установленного; копия с устаревшим блоком обновляется, не отвергается (рантайм
и его команды — [14](14-runtime.md)). Отдельный абзац разрешает копии, которые строит `vibe install`
(загрузочная полоса, проекция, преобразованные файлы). Релизная ветка, которую строит
`codkit publish`, файла не несёт — own-снимок публикации собирается без него; руками или чужим
инструментом файл в дереве форка не удаляют: дерево — это материализация patch set, и удаление там
прочтётся как работа. Копии не правят: `load` откажет `CK-E-STANDARDS-DRIFT`; правленую копию
удаляют и повторяют `load`. Ссылки на файл — из README продукта, из вмешательства patch set в README
форка — ставит владелец продукта сам, обдуманно; Codkit README не трогает. Для чистого экспорта
репозитория через `vibe scrape` две строки контракта — `[[classify]]` delete и `[[assert]]`
paths-absent для обоих путей — `load` вписывает в `vibevm/scrape/contract.toml` сам, управляемым
блоком между `# codkit:begin scrape` и `# codkit:end scrape` (внутри блока не править, своих строк с
этими id и путями не заводить). Контракта ещё нет — `load` так и скажет: выполните
`vibe scrape contract init`, затем `codkit standards load` ещё раз. Контракт по нестандартному пути
(`vibe scrape --contract`) Codkit не знает — для него строки печатает `codkit standards license`.

## До первой команды

`vibe.toml` продукта обязан существовать и содержать `[project]` — иначе exit `2` с hint про
`vibe init`: Codkit vibevm-проекты не создаёт. Файл обязан быть UTF-8 c LF; CR даёт `CK-E-CRLF`.

## Что нельзя

- Не править установленную копию под `vibevm/vibepacks/org.vibevm.codkit/`. Отклонение от стандарта
  — decision record в собственных спеках продукта со ссылкой на якорь стандарта. Поверх правок
  `load` отказывает `CK-E-STANDARDS-DRIFT` и перечисляет `modified` / `extra` / `missing`; рецепт —
  перенести правки в свои спеки, удалить каталог копии, повторить `load`.
- Не заводить свою запись `org.vibevm.codkit/<имя>` в `vibe.toml` вне блока: `load` откажет
  `CK-E-CONFIG` с номером строки — для любого поставляемого имени.
- Не редактировать внутри блока и не оставлять один маркер из двух: блок с одним маркером —
  `malformed`, `load` останавливается и просит починить руками; авто-починки нет.
- Не дописывать после `# codkit:end standards` ключи без собственного заголовка `[…]`: блок
  открывает таблицу зависимости, и такие ключи попадут в неё. `standards check` предупредит; новые
  таблицы добавляйте с заголовком.

## Новое издание и издание, расширенное на месте

Новая версия Codkit несёт новую версию пакета. `codkit standards load` кладёт каталог `v<новая>`
рядом со старым, переводит блок на новую точную версию и перечисляет старые каталоги как
`otherVersions`; после `vibe install` старый каталог удаляется рукой и коммитится вместе с
обновлённым `vibe.lock`.

Рулингом владельца 2026-09-07 издание **мутабельно**, пока не сказано иное: содержимое расширяется
на месте под тем же номером версии. Рулингом 2026-09-08 этот номер — **1.0.0**, версия разработки:
её несут все поставляемые пакеты (стандарты, навыки, библиотека рантайма), и она не поднимается
ни при какой правке. Каталоги `standards/v0.2.0` и `agent-skills/v0.1.0` переехали в `v1.0.0` без
изменения содержимого; в продукте, где стоят прежние версии, `codkit standards load` кладёт
`v1.0.0` рядом и перечисляет старые в `otherVersions`, а `codkit standards load --upgrade` их
удаляет и называет каждый каталог в выводе (`remove …`, `removed superseded version: …`; сухой прогон `--dry-run` печатает те же пути со словами `would remove superseded version: …` и ничего не удаляет). По байтам Codkit не отличает правку продукта от обновления
инструмента и не угадывает: копия с другими байтами — по-прежнему `drift`, `check` и `load`
отказывают, а `codkit standards load --upgrade` — явное слово «взять поставляемую копию». Он
печатает `replace`/`remove` пути, заменяет каталог пакета целиком, удаляет вытесненные каталоги
версий и печатает `next: vibe install --offline --force`: номер издания в `vibe.lock` тот же, байты
другие, обычный `vibe install` работу не переделает; следом `vibe skill install` обновляет проекцию
навыков. Правленую копию `LICENSE-CODKIT.md` `--upgrade` не чинит: её удаляют и повторяют `load`.

## Три лицензии, и ни одна не подменяет другую

- **Пакеты** — `LICENSE` и `REUSE.toml` внутри каталога каждого пакета описывают только этот пакет
  (UPL-1.0, та же лицензия, что у Codkit) и едут вместе с ним как часть побайтовой копии. Каждый
  файл пакета несёт заголовок или sidecar `<файл>.license`; `load` проверяет это до первой записи
  (`codkit license check` — та же проверка руками, exit `0` на поставляемом пакете).
- **Репозиторий продукта** — его корневой файл лицензии Codkit не читает, не копирует и не меняет;
  он никуда не уезжает.
- **Дерево форка** — файлы лицензии и notices форка и лицензионные поля `product.json` — апстримные
  файлы. Хотите другую лицензию на форке — это обычный артефакт дельты в patch set (config-overlay
  для полей `product.json`, resource-file или add-file патч для текстов), с владельцем, причиной и
  стражем; `REUSE.toml` для форка — тоже артефакт дельты.

`codkit standards load` печатает это примечание четырьмя строками `licence note:` при каждом
запуске. Пакет и стандарты — на английском языке; уведомление о лицензии в каждом файле —
по-английски и по-русски.
